Работа продолжается на готовых фичах Notify Mini: A — отписка, B — сортированный список подписчиков. Домашняя работа 4 в этот этап не входит.

## 1. Исходное состояние

7 октября 2026 года проверена ветка `practice-04-b` на коммите `2f76f48`. В отдельной рабочей папке есть обе фичи. Выполнены 8 тестов — все успешны ([вывод](evidence/baseline.txt)).

Ветка — указатель на историю изменений. Worktree — отдельная папка с файлами одной из веток; здесь она позволяет проверять B, не меняя файлы открытой практики 3.

Установлен OpenCode 1.18.32; презентация описывает 2.0.20. Используем API фактически установленной версии и проверяем его действиями.

## 2. Правила, skill и MCP

`AGENTS.md` ограничивает задачу: стандартная библиотека, данные в памяти, сохранение результатов практики 3. В `STYLE_GUIDE.md` задан snake_case — например, `cleaned_name` в отписке — и проверяемое форматирование. Агент прочитал эти файлы.

В проект скопирован уже установленный готовый `test-driven-development` вместе с `writing-good-tests.md`. OpenCode вызвал инструмент `skill` и прочитал reference ([подтверждение](evidence/skill.txt)). Правила проекта говорят, что делать и чего не менять; skill задаёт процедуру работы.

В отдельной временной копии воспроизведён цикл A: код до отписки с её тестами падает; сохранённая реализация A даёт 6 успешных тестов; полный проект даёт 8. Это новая учебная демонстрация, не доказательство того, как фича создавалась 2 октября ([вывод](evidence/replay-a.txt)).

Готовый внешний MCP `fetch` действительно вызван из OpenCode. Из официальной документации Python получено описание `set.discard`: удалить элемент, если он присутствует. Поэтому повторная отписка безопасна. Собственный MCP не создавался ([вызов и ответ](evidence/mcp.txt)).

Первый ответ модели содержал только обещание действий. После уточнения появились реальные инструменты. Также URL с якорем не заставил fetch вернуть только нужный раздел; агенту пришлось найти его в длинной странице. Наличие сообщения «начинаю» или статуса connected ещё не подтверждает выполненную работу.

## 3. Автоматическая проверка после правки

`scripts/check.sh` выполняет Ruff check, проверку форматирования и все 8 тестов демо. Ruff закреплён на версии 0.16.10 и запускается через `uvx`; первая установка может потребовать сеть. Проверки не исправляют файлы автоматически.

Для OpenCode 1.18.32 используется `tool.execute.after`: после `edit`, `write` или `apply_patch` плагин запускает фиксированный runner для изменённых файлов демо/проверок. Текст результата добавляется прямо к ответу инструмента, поэтому агент видит ошибку до следующего решения. Это отличается от pre-commit, который проверяет изменения перед коммитом.

Живая демонстрация: OpenCode временно поменял ожидаемый порядок имён на неправильный, получил FAIL с AssertionError, восстановил ожидание и получил PASS с 8 тестами OK. Правка файла журнала не вызвала проверку. Реализация фич и исходные тесты после эксперимента не изменились ([три вызова](evidence/hook.txt)).

Сам плагин проверен четырьмя автоматическими тестами на настоящих shell-процессах: ошибка runner, успешный apply_patch, отсутствие рекурсии от документации и остановка зависшего runner. До реализации три проверки падали, после — четыре из четырёх проходят ([вывод](evidence/hook-tests.txt)). На macOS/Linux таймаут 30 секунд завершает группу процессов проверки. Это учебная автоматизация, не изоляция от вредоносного кода.

API сверено с [исходником OpenCode 1.18.32](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/plugin/src/index.ts) и установленными типами. Пример `ctx.tool.hook` из слайдов 2.0.20 для этой установки не использовался.

## 4. Независимое ревью B

Родительская сессия OpenCode вызвала именно `task` с `subagent_type=explore`. Дочерняя сессия прочитала контракт и код, посмотрела diff B и выполнила общий runner. Подтверждённых проблем не найдено; решение — оставить B без изменений ([связь сессий и команды](evidence/review.txt)).

В тексте ревью была предложена дополнительная команда unittest из корня, которая не учитывает локальный импорт `service`. Она не использовалась как доказательство; проверенной командой остаётся `sh scripts/check.sh`. Это пример того, почему текст AI-ревью тоже нужно проверять.

Отдельное ревью новой автоматизации подтвердило четыре теста hook, восемь тестов демо и живые FAIL/PASS. Замечание касалось только упаковки ESM: runtime-файлы OpenCode оставлены локально, а manifest плагина включается явно ([результат](evidence/implementation-review.txt)).

## Как повторить проверки

Из корня репозитория: `sh scripts/check.sh`. Нужны Python 3.10+, Make и `uvx`; Ruff 0.16.10 устанавливается и кешируется через uvx. Проверки самого плагина: `node --test tests/check-after-edit.test.mjs` (проверено с Node 24.19.0). Node нужен только для этой дополнительной проверки; OpenCode выполняет плагин своим runtime.

Для OpenCode используется существующий `opencode.json` с VseLLM и fetch MCP. Ключ остаётся в пользовательском хранилище, в файлы практики не включается. В этой работе он передавался процессу через VSELLM_API_KEY без вывода в журнал.

## 5. Объединение

Ветка B с кодом и настройками локально объединена fast-forward в `practice4-unsubscribe` (619fca9). Fast-forward означает перемещение указателя A вперёд по уже существующей истории; коммиты A/B не переписывались. Основной каталог теперь открыт на этой ветке; `practice_03` сохранена отдельно.

Проверено именно объединённое состояние: 8 тестов демо, 4 теста плагина, Ruff, pre-commit и проверка whitespace прошли ([вывод](evidence/final-check.txt)). Из экспортированных текстовых выдержек удалены только конечные пробелы; результаты инструментов не изменялись.

## 6. Передача контекста

Новая сессия OpenCode без старой переписки прочитала `AGENTS.md` и `docs/HANDOFF.md`, правильно описала Notify Mini, A/B, ветку и ограничения. Она сама выполнила `git branch --show-current` и `sh scripts/check.sh`: ветка правильная, 8 тестов прошли ([подтверждение](evidence/handoff.txt)).

В первоначальном пересказе pre-commit был неточно привязан к стадированию. Уточнили правило: `git add` только готовит индекс, pre-commit срабатывает при `git commit`. Сессия перечитала правило и исправила объяснение. After-edit hook работает раньше, сразу после правки через инструмент OpenCode.
