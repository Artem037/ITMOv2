# Test-Driven Development (TDD)

## Overview

Write the test first. Watch it fail. Write minimal code to pass.

**Core principle:** If you didn't watch the test fail, you don't know if it tests the right thing.

**Violating the letter of the rules is violating the spirit of the rules.**

## When to Use

**Always:**
- New features
- Bug fixes
- Refactoring
- Behavior changes

**Exceptions (ask your human partner):**
- Throwaway prototypes
- Generated code
- Configuration files

Thinking "skip TDD just this once"? Stop. That's rationalization.

Почему set.discard подходит для unsubscribe отсутствующего имени:
- Требование B: «missing is safe» — отсутствие подписчика не должно приводить к исключению, а результат должен быть {"unsubscribed": False}. В тесте test_unsubscribe_missing_is_safe это закреплено: ловится KeyError как недопустимый, и ожидается unsubscribed=False, а множество остаётся пустым.
- В service.py (строки 15–17) реализовано:
  - was_subscribed = cleaned_name in subscribers
  - subscribers.discard(cleaned_name)
  - return {"unsubscribed": was_subscribed}
- discard в отличие от remove не поднимает KeyError при отсутствии элемента. Это ровно соответствует безопасной семантике «удали, если есть; иначе ничего не делай».
- Факт из официальной документации Python (получено MCP fetch, URL см. выше, вызов со start_index=146000):
  - Цитата раздела Set Types — set, frozenset: “set.discard(elem, /): Remove element elem from the set if it is present.” То есть discard удаляет элемент, только если он присутствует, и не бросает исключений при отсутствии.
- Благодаря проверке membership перед вызовом discard код корректно возвращает True/False, а discard обеспечивает отсутствие KeyError, полностью соответствуя тесту и README.
