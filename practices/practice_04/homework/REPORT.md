# Домашняя работа 4: планировщик загородных поездок

Задача: выбрать время выхода так, чтобы согласовать редкие рейсы и
сократить полное время в пути. Контрольный пример — Альпийский переулок →
Малый Лужский каньон, 14.10.2026, выход 06:00–10:00.

## Устройство и польза компонентов

Skill собирает исходные данные и источники, вызывает MCP, объясняет варианты.
Собственный MCP `plan_departures` считает достижимые пересадки, время выхода,
ожидание и отбирает до пяти разных выходов. Один алгоритм используется
сервером и CLI, поэтому проверяем арифметику независимо от текста агента.

AGENTS задаёт правила разработки и проверки источников. Готовый fetch MCP
нужен для чтения публичных расписаний. Hook после значимой правки запускает
runner и возвращает результат агенту; это помогает заметить поломку сразу.
TDD skill из практики сохранён для разработки. Новые подключения имеют
конкретные роли, их количество не является целью работы.

## Проверка результата

Тесты задают ручные ожидаемые значения, включая редкую пересадку на границе
запаса и опоздание на минуту. Полные даты проверены на переходе через полночь.
Источники с неподтверждённым статусом не дают подтверждённых вариантов.
При нехватке данных возвращается `needs_data`, при отсутствии подходящей
комбинации в полном наборе — `no_routes`, ошибочный вход вызывает ошибку.

Протокольный тест поднимает настоящий stdio-сервер, получает список tools,
вызывает инструмент правильно, затем с отрицательным запасом, затем снова
правильно. В OpenCode этот же сценарий выполнен отдельно, сохранены callID.

Независимая проверка skill показала лишнюю худшую комбинацию с повторным
временем выхода. Добавлен падающий тест, отбор исправлен, повторный прогон
дал два полезных выхода. На простом baseline без skill агент уже считал
верно; искусственное улучшение точности не заявляется.

Итоговое [ревью](evidence/review.md) выявило два существенных дефекта:
устаревшее расписание могло дать ложное `no_routes`, а большой набор рейсов
— превысить таймаут. Добавлены проверки покрытия дат, доказательства пустого
расписания и лимит 50 000 шагов перебора. Регрессии сначала падали, затем
прошли. [Финальные проверки](evidence/final-check.txt): 28 тестов домашки,
8 тестов прежнего демо и 6 тестов hook; Ruff и проверка diff пройдены.

В реальном прогоне агент повторно получил страницу СЗППК встроенным
`webfetch`, затем вызвал собственный MCP. Его неточная фраза «fetch MCP»
исправлена в evidence: этот прогон не доказывает вызов готового fetch MCP.

## Ограничения

В этой версии агент извлекает данные из официальных страниц; отдельного
Яндекс API-адаптера нет. Ключ не нужен. Расписание не обновляется в фоне.
Расчёт сравнивает подготовленные цепочки, максимум три расписанных этапа;
городские и пешие части являются оценками. Метрики ожидания/пересадок
относятся к расписанным этапам, городской путь описан отдельно.

У контрольного маршрута промежуточное автобусное время не подтверждено.
Проверяемая альтернатива включает 9,2 км пешком. Это существенное условие
поездки, его нельзя скрывать за короткой таблицей. [Источники](SOURCE_CHECK.md).

## Сценарий защиты на 5–7 минут

1. Объяснить задачу и показать свой skill с двумя ресурсами.
2. Показать AGENTS и роли двух MCP-подключений.
3. Запустить `make step4`; объяснить один тест редкой пересадки.
4. В OpenCode загрузить skill и вызвать MCP на учебном входе. Показать
   ожидаемый выход 09:35, затем ошибку отрицательного запаса и исправление.
5. Показать evidence hook с реальным FAIL/PASS и объяснить возврат агенту.
6. Открыть реальный пример, отличить часы расписания от оценок, сверить
   одну строку вручную. Объяснить, почему не выдуманы ещё два варианта.
7. Рассказать собственные наблюдения из reflection.md после его заполнения.
