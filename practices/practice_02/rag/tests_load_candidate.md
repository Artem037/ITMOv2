# Нагрузочные проверки (кандидат)

Этот вариант уточняет исходный `tests_load.md` на основе разрешённых источников с явным разделением: подтверждённые требования, конфигурация тестов и гипотезы/TBD. Для каждого факта указан источник.

## Использованные источники и факты (evidence)

- CASE.md — правила репозитория:
  - `SEC-1`: до внешнего LLM из diff удаляются токены, пароли и приватные ключи. [CASE.md:64]
  - `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413. [CASE.md:65]
  - `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ. [CASE.md:66]
  - `OBS-1`: лог содержит только `request_id`, длительность и статус; содержимое diff и ответа не логируется. [CASE.md:70]
- problem.md — подтверждённые измеримые метрики цели: доля утечек секретов в LLM (цель 0%), доля oversized diff с вызовом LLM (цель 0%), доля контролируемых таймаутов/ошибок LLM (цель 100%, timeout ≤10s), доля ответов, соответствующих `OUT-1`/`QA-1` (цель 100%), отсутствие утечек diff/LLM-ответа в логи (цель 0 утечек). [problem.md:15-19]
- context.md — известные/неизвестные данные: фактическая производительность и допустимая интенсивность запросов отсутствуют; значения для load‑тестов — проверяемая гипотеза. [context.md:63-66]
- adr.md — архитектурные ограничения/компоненты для влияния на тестирование: контролируемый pipeline, redaction перед внешним вызовом, timeout 10s и маппинг на контролируемые ошибки зависимости (504/502 — локальное решение, ADR в статусе proposed). [adr.md:13-21][adr.md:23-31]
- tests_load.md — исходные сценарии и текущая классификация меток; реальный внешний LLM не используется в регулярном load‑тесте (практическая установка авторов файла). [tests_load.md:5-12]

## Подтверждённые требования (confirmed requirements)

- Oversized diff отклоняется с HTTP 413. [CASE.md:65]
- До внешнего LLM из diff удаляются секреты. [CASE.md:64]
- Вызов внешнего LLM ограничен timeout 10 секунд, ошибка преобразуется в контролируемый ответ. [CASE.md:66]
- Логи не содержат diff и ответа LLM; только `request_id`, длительность и статус. [CASE.md:70]
- Для oversized diff вызов LLM не должен происходить как следствие `API-1`. Evidence: цель «0% вызовов LLM для >20 001» в метриках. [problem.md:16]

Примечание: SLO/порогов производительности (throughput, целевой RPS/конкурентность, latency p95/p99, success rate, availability SLO) в подтверждённых источниках нет. [context.md:63-66]

## Конфигурация тестов (test configuration)

- Использовать stub/spy вместо реального внешнего LLM в нагрузочных прогонах, чтобы избегать неконтролируемой стоимости и исключить отправку тестовых секретов. Источник: текущая практика из tests_load.md. [tests_load.md:12]
- Параметры прогонов и нагрузки как настройки эксперимента, а не требования: RPS, длительность, число одновременных клиентов, latency stub и наборы входных размеров (20 000 и 20 001 символов). [tests_load.md:5-10]
- Использование маркерных секретов для проверки отсутствия утечек в логах. [tests_load.md:10]

## Метрики к наблюдению (metrics to observe)

- Доля тестовых секретов, дошедших до LLM‑spy: цель 0% (SEC‑1). [problem.md:15]
- Доля oversized diff (>20 000) с вызовом LLM: цель 0% (API‑1). [problem.md:16]
- Доля timeout/ошибок LLM с контролируемым ответом; timeout не позже 10 секунд (REL‑1). [problem.md:17]
- Доля успешных ответов, соответствующих `OUT-1` и `QA-1`: цель 100%. [problem.md:18]
- Утечки diff или LLM‑ответа в лог: цель 0. [problem.md:19]
- Дополнительные наблюдаемые показатели для нагрузок из исходного файла как вспомогательные метрики (не требования): RPS/throughput, p95/p99 latency, error rate, распределение статусов, RSS/память процесса, число занятых workers, recovery time, объём логов и поиск маркеров. [tests_load.md:7-10]

## Гипотезы / TBD (не подтверждено источниками)

- Численные нагрузки: 50 RPS на 10 минут (LT‑1), 10 RPS и 20 клиентов на 10 минут (LT‑2), 5 RPS на 2 минуты (LT‑3). [tests_load.md:7-9]
- Пороговые латентности: p95 ≤ 200 мс (LT‑1, LT‑3 /health), p95 ≤ 500 мс (LT‑2). [tests_load.md:7-9]
- Уровень успеха: success ≥99% (LT‑2). [tests_load.md:8]
- Предельное время контролируемого ответа «не позже 11 сек» (LT‑3) — расходится с подтверждённым timeout 10 сек по `REL-1`; следует использовать 10 сек как требование, «11 сек» — гипотеза и не подтверждённый запас. [tests_load.md:9][CASE.md:66]
- Ограничение «на каждый запрос не более одного итогового metadata‑event» — не закреплено в источниках. [tests_load.md:10]

## Классификация сценариев из tests_load.md

- LT‑1 Валидация без внешнего LLM
  - Требования: HTTP 413 для 20 001+; 0 вызовов LLM для oversized. [CASE.md:65][problem.md:16]
  - Конфигурация: 50 RPS, 10 минут; смесь 20 000/20 001; stub adapter. [tests_load.md:7]
  - Гипотезы: p95 ≤ 200 мс; 0 неконтролируемых 5xx (целевой стиль, но не из CASE.md). [tests_load.md:7]
  - Метрики: RPS, p95/p99, error rate, call count. [tests_load.md:7]

- LT‑2 Номинальный LLM stub
  - Требования: отсутствуют явные производственные пороги; наблюдаем соответствие метрикам из problem.md при happy‑path. [problem.md:15-19]
  - Конфигурация: 10 RPS, 10 минут, 20 клиентов; stub latency 100 мс. [tests_load.md:8]
  - Гипотезы: p95 ≤ 500 мс; success ≥99%; память не растёт монотонно. [tests_load.md:8]
  - Метрики: Latency, throughput, status distribution, RSS. [tests_load.md:8]

- LT‑3 Timeout saturation
  - Требования: 100% контролируемых ответов при зависшем LLM; timeout 10 секунд. [CASE.md:66][problem.md:17]
  - Конфигурация: 5 RPS, 2 минуты; stub никогда не отвечает. [tests_load.md:9]
  - Гипотезы: «не позже 11 сек»; `/health` p95 ≤ 200 мс после снятия нагрузки. [tests_load.md:9]
  - Метрики: duration, 504 rate, число занятых workers, recovery time. [tests_load.md:9]

- LT‑4 Безопасность логов под нагрузкой
  - Требования: 0 маркеров секретов в логах; логи без diff/LLM‑ответа; только метаданные. [CASE.md:70][tests_load.md:10]
  - Конфигурация: повтор LT‑2, уникальные маркерные секреты. [tests_load.md:10]
  - Гипотезы: не более одного итогового metadata‑event на запрос. [tests_load.md:10]
  - Метрики: объём логов и скан маркеров. [tests_load.md:10]

## Отсутствующие источники для производственных SLO

- Нет подтверждённых источников для throughput, целевого RPS, concurrency target, latency p95/p99 порогов, success rate или availability SLO — источник отсутствует. [context.md:63-66]

## Примечание по ADR

- Маппинг ошибок зависимости на HTTP 504/502 указан в ADR (proposed) и может влиять на критерии проверки статусов под нагрузкой, но не является подтверждённым требованием Practice 1. [adr.md:17][adr.md:23-31]
