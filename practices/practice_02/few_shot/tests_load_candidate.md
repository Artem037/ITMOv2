# Нагрузочные проверки (кандидат)

Исходник не менялся: practices/practice_01/tests_load.md.
Цель кандидата — сохранить полезные сценарии и явно разделить:
- Hard Requirements — подтверждённые правила из CASE.md с ссылками;
- Test Parameters — конкретные настройки прогона/baseline;
- Hypotheses — инженерные гипотезы для baseline, не SLO.

Связанные требования из CASE.md:
- API-1: diff длиннее 20 000 символов отклоняется с HTTP 413.
- REL-1: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- SEC-1: до внешнего LLM из diff удаляются токены, пароли и приватные ключи.
- OBS-1: в лог пишутся только request_id, длительность и статус; содержимое diff и ответа модели не логируется.

Легенда меток:
- [ТРЕБОВАНИЕ] — подтверждённое правило из CASE.md;
- [ПАРАМЕТР] — настройка конкретного тестового прогона/baseline;
- [ГИПОТЕЗА] — предварительный порог для baseline, не является утверждённым SLO.

## Сценарии

### LT-1. Валидация без внешнего LLM

- Test Parameters:
  - 50 RPS [ПАРАМЕТР], 10 минут [ПАРАМЕТР]
  - Смесь диффов: 20 000 [ПАРАМЕТР] и 20 001 [ПАРАМЕТР] символов
  - LLM adapter: stub [ПАРАМЕТР]
- Hard Requirements:
  - Для oversized (diff > 20 000 символов) возвращается HTTP 413 [ТРЕБОВАНИЕ API-1]
  - В данном тесте ожидаем 100% HTTP 413 для oversized — производный критерий приёмки для детерминированной проверки API-1 (не отдельное требование CASE.md)
- Hypotheses:
  - p95 ≤ 200 мс [ГИПОТЕЗА — источника в CASE.md нет]
  - 0 неконтролируемых 5xx [ГИПОТЕЗА]
  - Для oversized 0 LLM calls [ГИПОТЕЗА]
- Что измеряем: RPS, p95/p99, error rate, LLM call count.
- Evidence: отчёт k6/Locust и метрики/spy.

### LT-2. Номинальный LLM stub

- Test Parameters:
  - 10 RPS [ПАРАМЕТР], 10 минут [ПАРАМЕТР]
  - 20 одновременных клиентов [ПАРАМЕТР]
  - Stub latency 100 мс [ПАРАМЕТР]
- Hard Requirements:
  - Логи не содержат diff/LLM-контента, только request_id/длительность/статус [ТРЕБОВАНИЕ OBS-1]
- Hypotheses:
  - p95 ≤ 500 мс [ГИПОТЕЗА]
  - success ≥ 99% [ГИПОТЕЗА]
  - Память не растёт монотонно [ГИПОТЕЗА]
- Что измеряем: latency, throughput, статус-коды, RSS.
- Evidence: нагрузочный отчёт и график ресурсов.

### LT-3. Timeout saturation

- Test Parameters:
  - 5 RPS [ПАРАМЕТР], 2 минуты [ПАРАМЕТР]
  - Stub никогда не отвечает [ПАРАМЕТР]
- Hard Requirements:
  - 100% запросов получают контролируемый ответ [ТРЕБОВАНИЕ REL-1]
  - Таймаут внешнего LLM-вызова 10 секунд [ТРЕБОВАНИЕ REL-1]
- Hypotheses:
  - Ответ клиенту «не позже 11 сек» [ГИПОТЕЗА — верхняя граница SLA ответа системы; источник в CASE.md отсутствует]
  - После снятия нагрузки `/health` p95 ≤ 200 мс [ГИПОТЕЗА]
- Что измеряем: общая длительность, доля 504/ошибок, число занятых workers, время восстановления.
- Evidence: отчёт и application metrics.

### LT-4. Безопасность логов под нагрузкой

- Test Parameters:
  - Повторить LT-2 [ПАРАМЕТР]
  - Уникальные маркерные секреты в diff [ПАРАМЕТР]
- Hard Requirements:
  - 0 маркеров секретов в логах (содержимое diff/LLM не логируется) [ТРЕБОВАНИЕ OBS-1]
  - Секреты удаляются до внешнего LLM [ТРЕБОВАНИЕ SEC-1]
- Hypotheses:
  - На каждый запрос не более одного итогового metadata-event [ГИПОТЕЗА]
- Что измеряем: объём логов, поиск маркеров, поведение санитайзера.
- Evidence: sanitized log scan.

Примечание: реальный внешний LLM не используется в регулярном load-тесте, чтобы не создавать неконтролируемую стоимость и не отправлять тестовые секреты. Отдельный staging smoke-тест выполняется только после согласования лимитов и бюджета.
