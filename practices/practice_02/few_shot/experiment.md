# Few-shot

- Артефакт Практики 1: practices/practice_01/tests_load.md
- Что хотим улучшить: явно отделить подтверждённые требования из CASE.md от параметров baseline-прогонов и инженерных гипотез; убрать видимость выдуманных SLO.

## Примеры

### Хороший результат

Timeout внешнего LLM равен 10 секунд. Это подтверждённое требование с источником REL-1 из CASE.md.

### Плохой результат

p95 ≤ 500 мс и success ≥ 99%. Источник этих значений не указан, поэтому они выглядят как выдуманный production SLO.

## Запрос

Нужно улучшить tests_load.md без изменения исходного файла. Хороший результат явно разделяет:
1. обязательное требование с источником;
2. параметр самого эксперимента;
3. неподтверждённую гипотезу.

Плохой результат — представлять произвольные RPS, p95 или success rate как утверждённый SLO.

Проанализируй текущий practices/practice_01/tests_load.md. Для каждого числового значения определи и пометь:
- подтверждённое требование (с указанием источника из CASE.md);
- параметр эксперимента;
- гипотеза (если источника нет — прямо так и напиши).

Не придумывай новые SLO/RPS/latency/availability цели. Сохрани полезные сценарии, но явно раздели hard requirements, test parameters и hypotheses. Исходный файл не менять; создай улучшенную копию в practices/practice_02/few_shot/tests_load_candidate.md.

## Что получили

Классификация чисел в исходном tests_load.md:
- ПАРАМЕТРЫ тестов: 50 RPS; 10 минут; смесь 20 000/20 001 символов; stub adapter; 10 RPS; 20 одновременных клиентов; stub latency 100 мс; 5 RPS; 2 минуты; «stub не отвечает»; повтор LT-2; маркерные секреты.
- ИНЖЕНЕРНЫЕ ГИПОТЕЗЫ (нет источника в CASE.md): p95 ≤ 200 мс; 0 неконтролируемых 5xx; 0 LLM calls при oversized; p95 ≤ 500 мс; success ≥ 99%; «память не растёт монотонно»; «не позже 11 секунд»; «/health p95 ≤ 200 мс после снятия нагрузки»; «не более одного итогового metadata-event».
- ТРЕБОВАНИЯ из CASE.md: 100% HTTP 413 для oversized (API-1); таймаут внешнего LLM-вызова 10 секунд и контролируемый ответ при ошибке (REL-1); отсутствие контента diff/LLM в логах (OBS-1); удаление секретов до внешнего LLM (SEC-1, особенно релевантно для LT-4).

Что изменили: создали practices/practice_02/few_shot/tests_load_candidate.md — переписали сценарии LT-1..LT-4, где для каждого сценария отдельно перечислены Test Parameters, Hard Requirements (с ссылками на CASE.md) и Hypotheses. Убрали видимость неподтверждённых SLO: числа без источника помечены как гипотезы.

## Что изменили в исходном артефакте

- Файл и раздел: practices/practice_01/tests_load.md — исходник (не менялся); practices/practice_02/few_shot/tests_load_candidate.md — предлагаемая новая версия.
- Изменение: явное разделение требований/параметров/гипотез; добавлен список подтверждённых требований из CASE.md и ссылки (API-1, REL-1, SEC-1, OBS-1) внутри сценариев.
- Как проверили: сопоставили все числовые значения с practices/practice_01/CASE.md (там нет целей RPS/p95/success); проверили, что каждая жёсткая граница имеет ссылку; перечитали кандидат на отсутствие новых «SLO» без источника.

## Итоги независимого ревью

Независимая команда отметила сильные стороны и ограничения эксперимента.

- Положительное: хорошие/плохие примеры действительно помогли разделить требования, параметры и гипотезы; отдельная candidate‑копия делает влияние эксперимента наблюдаемым.
- Ограничение интерпретации: эффект Few‑shot частично смешан с прямыми инструкциями prompt — в запросе уже подробно описано, как классифицировать элементы. Отдельный контрольный запуск без примеров не проводился, поэтому вклад самих примеров не изолирован.
- Уточнение требований: формулировка «100% HTTP 413» — это производный критерий приёмки для детерминированной проверки правила API‑1, а не буквальное требование из CASE.md. Исправлено в candidate: в LT‑1 закрепили API‑1 как требование, а «100%» пометили как derived acceptance criterion.
