# Нагрузочные проверки (Candidate)

В CASE.md нет продуктового SLO и числовых целей по latency/throughput/availability. Значения ниже классифицированы:
- [ТРЕБОВАНИЕ] — подтверждённое правило из CASE.md (с указанием ID);
- [ПАРАМЕТР] — настройка данного тестового прогона/baseline;
- [ГИПОТЕЗА] — инженерный порог для наблюдения в baseline, не является утверждённым SLO.

## Подтверждённые требования (из CASE.md)

- API-1: diff длиной более 20 000 символов отклоняется с HTTP 413. [ТРЕБОВАНИЕ; CASE.md `API-1`]
- REL-1: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ. [ТРЕБОВАНИЕ; CASE.md `REL-1`]
- SEC-1: до внешнего LLM из diff удаляются токены, пароли и приватные ключи. [ТРЕБОВАНИЕ; CASE.md `SEC-1`]
- OBS-1: в лог пишутся только `request_id`, длительность и статус; содержимое diff и ответа модели не логируется. [ТРЕБОВАНИЕ; CASE.md `OBS-1`]

Примечания:

- Регулярный load-тест выполняется со stub/spy вместо реального внешнего LLM, чтобы избежать неконтролируемой стоимости и отправки тестовых секретов. Отдельный staging smoke-тест с реальным LLM возможен только после согласования лимитов и бюджета.
- Для [ГИПОТЕЗ] фиксируются наблюдаемые метрики и значения baseline; pass/fail критерии устанавливаются только для [ТРЕБОВАНИЕ].

## Как использовали AI

- Для чего: привести план нагрузочных проверок к проверяемой структуре без выдуманных SLO, отделив требования CASE.md от параметров и гипотез.
- Источники: CASE.md (`API-1`, `REL-1`, `SEC-1`, `OBS-1`), текущий `tests_load.md` как исходный черновик.
- Что проверили самостоятельно: каждое числовое значение классифицировано и снабжено способом evidence; пороги SLO не вводились.
