# P1-01: zero-shot baseline

## Prompt

`Посмотри PR и найди проблемы.`

К запуску был приложен только `TRAINING_PR.diff`. Формулировка короче рекомендованной в `CASE.md`, но не добавляет контекст, примеры или правила и поэтому остаётся корректным zero-shot baseline.

## Инструмент и модель

OpenCode / VseLLM / `openai/gpt-5`.

## Answer

Ниже — findings-first код-ревью по TRAINING_PR.diff. Указываю проблемы с отсылками к файлам и строкам из diff-контента.
Проблемы (по серьёзности)
- Critical — app/api.py: create_review читает payload"diff" напрямую
- Строки: @app.post("/api/reviews") → def create_review(payload: dict) -> dict[str, str]: → return review_service.review(payload["diff"])
- Риск: KeyError при отсутствии ключа "diff" в теле запроса → 500 вместо ожидаемой 4xx-валидации.
- Также нет проверки типа значения: любые типы пройдут внутрь сервиса, валидация отсутствует.
- Critical — app/api.py: отсутствие обработчиков ошибок для LLM/сервиса
- Строки: return review_service.review(payload["diff"])
- Риск: исключение из review_service.review/llm.generate приведёт к 500. Нет контролируемых ответов/маппинга ошибок (например, 503/504).
- High — app/review_service.py: промпт без разграничителей и защиты от prompt injection
- Строки: prompt = f"Review this pull request and find problems:\n{diff}"
- Риск: содержимое diff напрямую встраивается в промпт без явных границ (например, тройные кавычки/маркер начала-конца) и без инструкций по игнорированию пользовательских указаний. Повышает вероятность prompt injection и плохой детерминированности ответа.
- High — app/review_service.py: нет ограничений на размер входа/токенов
- Строки: те же, что выше.
- Риск: большой diff может выбить модель по лимиту токенов или привести к деградации/исключениям. Нет обрезки, суммаризации, chunking или graceful degradation.
- Medium — app/api.py: нет схем запроса/ответа (Pydantic)
- Строки: def create_review(payload: dict) -> dict[str, str]:
- Риск: отсутствует декларативная валидация/документация. Автогенерируемая OpenAPI будет неточной, клиенты не увидят контракт. Сервер не вернёт 422 при невалидном теле.
- Medium — app/api.py: синхронный обработчик с потенциально долгим вызовом LLM
- Строки: def create_review(...):
- Риск: при сетевом LLM это долгий блокирующий вызов; в FastAPI sync хендлеры уходят в threadpool, но без таймаута/ограничений можно занять воркеры и получить деградацию.
- Low — app/review_service.py: возвращение транспортного dict из доменного сервиса
- Строки: return {"comment": answer}
- Замечание: сервис смешивает доменную логику и формат ответа API. Обычно сервис возвращает доменную сущность/строку, а слой API формирует wire-формат.
- Low — app/review_service.py: косметическая смена сигнатуры Protocol
- Строки: def generate(self, prompt: str) -> str: с телом ...
- Комментарий: это валидно, но стайл-гайд мог предпочитать однострочник как было ранее. Функционально без изменений.
- Low — app/api.py: зависимость на app.dependencies.review_service
- Строки: from app.dependencies import review_service
- Риск: если объект не инициализирован или не импортируется, будет ImportError на старте. В diff не видно, как он создаётся; это потенциальный источник падений при неверной конфигурации.
Открытые вопросы
1. Какой ожидаемый контракт API при невалидном теле запроса? Нужен ли 422 с деталями валидации?
2. Есть ли требования по лимиту размера diff и времени ответа? Нужны ли таймауты/ретраи для LLM?
3. Требуются ли меры против prompt injection (разделители, system prompt, escape)? Каков уровень доверия к источнику diff?
4. Нужен ли стабильный формат ответа (schema) и поля помимо "comment" (например, список findings с severities)?
Рекомендуемые изменения (кратко)
1. Ввести Pydantic-модели:
- Request: поле diff: str (обязательное, с базовой валидацией длины).
- Response: schema с полем comment: str или более структурированный результат.
2. Защитить вызов LLM:
- Добавить явные разделители контента diff (например, тройные кавычки) и инструкции для модели игнорировать внешние указания внутри diff.
- Добавить ограничение длины/препроцессинг diff (обрезка/суммаризация/Chunking).
- Ввести таймаут, обработку исключений и маппинг на 5xx/4xx.
3. Убрать прямой доступ к payload["diff"]:
- Использовать валидированную модель; для отсутствующего поля вернуть 422 с сообщением.
4. Разделить слои:
- Пусть ReviewService.review возвращает доменную сущность/строку; формирование HTTP-ответа оставить контроллеру.
5. Тесты:
- Успешный кейс с валидным diff.
- Отсутствующий diff → 422.
- Большой diff → контролируемая деградация или 413, если так решите.
- Исключение из LLM → предсказуемый 503/504.
Если подтвердите ожидаемое поведение по валидации и защите от prompt injection, подготовлю патч с минимальными правками: Pydantic модели, обработчики ошибок, безопасный промпт с разделителями и базовым лимитом на размер diff.
