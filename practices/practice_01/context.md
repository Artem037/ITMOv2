## Context Pack для первого рабочего сценария

### Цель и вход

- Цель: выдать человеку краткое, доказательное и воспроизводимое ревью одного PR.
- Вход: содержимое `TRAINING_PR.diff`; граница размера — не более 20 000 символов.
- Текущий путь: endpoint передаёт `payload["diff"]` в `ReviewService.review`, сервис формирует prompt и вызывает внешний LLM.

### Релевантные правила

| ID | Правило |
|---|---|
| `SEC-1` | До внешнего LLM из diff удаляются токены, пароли и приватные ключи. |
| `API-1` | Diff длиннее 20 000 символов отклоняется с HTTP 413. |
| `REL-1` | Внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ. |
| `OUT-1` | Ответ содержит `summary`, `risks`, `checks`; `risks` — максимум три элемента с `file`, `line`, `evidence`, `risk`. |
| `SCOPE-1` | Сервис только советует и не пишет код, не approve и не merge PR. |
| `QA-1` | Каждый риск подтверждён строкой diff или правилом репозитория. |
| `OBS-1` | В лог попадают только `request_id`, длительность и статус; diff и ответ LLM не логируются. |

Правила о `snake_case` таблиц и frontend-i18n исключены: в данном diff нет базы данных и пользовательского интерфейса.

### Формат результата

- `summary`: одно-два предложения о фактическом изменении.
- `risks`: не более трёх наиболее существенных рисков; у каждого есть `file`, `line`, `evidence`, `risk`.
- `checks`: воспроизводимые проверки для найденных рисков.

### Полномочия и ограничения

- AI может анализировать только diff и перечисленные правила.
- AI не меняет код и внешние системы, не выполняет approve/merge и не принимает решение за ревьюера.
- Отсутствие кода в diff означает «не показано/нужно проверить», а не доказанное отсутствие во всём репозитории.

### Примеры качества

Хороший: `app/review_service.py:14` вставляет исходный `diff` в prompt без показанного шага редактирования секретов; это нарушает `SEC-1`. Проверка — передать тестовый token и убедиться, что LLM-spy получил `[REDACTED]`.

Плохой: «Код можно улучшить, добавьте тесты». Здесь нет строки, правила, доказательства и способа проверки.

### Что пока неизвестно

- Реализация `app.dependencies.review_service` и конкретного LLM-клиента.
- Наличие глобальных FastAPI middleware/exception handlers вне diff.
- Фактическая производительность и допустимая интенсивность запросов; значения для load-тестов пока являются проверяемой гипотезой.
- Требуемый HTTP-статус для timeout/ошибки LLM: `REL-1` требует контролируемый ответ, но не задаёт код.

## Как использовали AI

- Для чего: собрать единый проверяемый Context Pack и согласовать остальные десять артефактов.
- Тип промпта: homework master prompt.
- Строка в [`prompts.md`](prompts.md): `P1-03`.
- Что проверили и исправили сами: отделили факты diff от правил `CASE.md`, исключили нерелевантные правила и пометили неизвестное вместо выдумывания реализации.
