# Проблема и метрики

## Проблема

- Пользователь: разработчик или ревьюер, который хочет быстро получить предварительный список доказуемых рисков в PR.
- Ситуация: новый `POST /api/reviews` принимает diff и отправляет его во внешний LLM.
- Что происходит сейчас: показанный в diff путь напрямую читает невалидированный словарь, передаёт исходный diff в LLM и возвращает свободный ответ в поле `comment`.
- Почему это мешает: секрет может покинуть доверенный контур, слишком большой запрос или ошибка LLM не имеют заданного контролируемого пути, а свободный ответ трудно проверить и использовать повторно.
- Что не входит в задачу: автоматическое изменение кода, approve/merge PR, анализ файлов вне diff и требования, отсутствующие в `CASE.md`.

## Метрики

| Метрика | Baseline / способ замера | Цель | Когда измеряем | Источник evidence |
|---|---|---|---|---|
| Доля тестовых секретов, дошедших до LLM-spy | В показанном пути шаг редактирования отсутствует; прогнать набор токенов, паролей и приватных ключей. | 0% секретов; 100% заменены на `[REDACTED]`. | На каждый PR и перед релизом. | Unit + integration проверки `SEC-1`. |
| Доля diff > 20 000 символов, для которых вызван LLM | В endpoint проверка не показана; отправить размеры 20 000 и 20 001. | 0% для 20 001+; HTTP 413, LLM не вызван. | На каждый PR. | Integration/E2E проверки `API-1`. |
| Доля timeout/ошибок LLM с контролируемым ответом | В изменённых строках обработка не показана; LLM-stub зависает и выбрасывает исключение. | 100% завершаются согласованной ошибкой; timeout не позже 10 секунд. | На каждый PR и в pre-release. | Integration/E2E проверки `REL-1`. |
| Доля успешных ответов, соответствующих `OUT-1` и `QA-1` | Текущий результат — `{"comment": answer}`, то есть 0 из 1 проверенного ответа соответствует целевой схеме. | 100% ответов имеют `summary`, `risks`, `checks`; не более трёх доказанных рисков. | На каждый PR. | Schema/unit и E2E проверки. |
| Утечки diff или LLM-ответа в лог | Проверяется capture логов на happy path и ошибке; реализация логирования в diff не показана. | 0 утечек; 100% записей содержат только `request_id`, duration, status. | На каждый PR и аудит релиза. | Integration-проверка `OBS-1`. |

## Почему изменение метрик подтвердит решение проблемы

Метрики покрывают четыре наблюдаемые границы: конфиденциальность до внешнего вызова, ранний отказ для недопустимого входа, устойчивость зависимости и проверяемость результата. Их можно измерить stub/spy-компонентами без субъективной оценки качества текста LLM.

## Как использовали AI

- Для чего: преобразовать правила кейса в измеримые критерии результата.
- Тип промпта: homework master prompt.
- Строка в [`prompts.md`](prompts.md): `P1-03`.
- Что проверили и исправили сами: не выдавали отсутствие строк в diff за доказательство отсутствия глобальных middleware; целевые значения связали с конкретными правилами.
