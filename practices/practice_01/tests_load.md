# Нагрузочные проверки

В `CASE.md` нет throughput/SLO, а реальная LLM-инфраструктура не дана. Поэтому числа ниже — стартовая инженерная гипотеза для baseline, а не подтверждённое требование. После первого staging-прогона владелец сервиса должен утвердить или изменить пределы.

| ID / сценарий | Нагрузка и длительность | Предварительный допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| `LT-1` Валидация без внешнего LLM | 50 RPS, 10 минут; смесь 20 000 и 20 001 символов; stub adapter. | p95 ≤ 200 мс; 0 неконтролируемых 5xx; для oversized 100% HTTP 413 и 0 LLM calls. | RPS, p95/p99, error rate, call count. | Отчёт k6/Locust и метрики spy. |
| `LT-2` Номинальный LLM stub | 10 RPS, 10 минут, 20 одновременных клиентов; stub latency 100 мс. | p95 ≤ 500 мс; success ≥99%; память не растёт монотонно. | Latency, throughput, status distribution, RSS. | Нагрузочный отчёт и график ресурсов. |
| `LT-3` Timeout saturation | 5 RPS, 2 минуты; stub никогда не отвечает. | 100% запросов получают контролируемый ответ не позже 11 сек; после снятия нагрузки `/health` p95 ≤200 мс. | Duration, 504 rate, число занятых workers, recovery time. | Отчёт и application metrics. |
| `LT-4` Безопасность логов под нагрузкой | Повторить `LT-2` с уникальными маркерными секретами. | 0 маркеров diff/LLM response в логах; на каждый запрос не более одного итогового metadata-event. | Объём логов и поиск маркеров. | Sanitized log scan. |

Реальный внешний LLM не используется в регулярном load-тесте, чтобы не создавать неконтролируемую стоимость и не отправлять тестовые секреты. Отдельный staging smoke-test выполняется только после согласования лимитов и бюджета.

## Как использовали AI

- Для чего: сформулировать безопасный baseline нагрузки при отсутствии продуктового SLO.
- Тип промпта: homework master prompt.

- Что проверили и исправили сами: явно обозначили числа как гипотезу и исключили реальный внешний LLM из массовой нагрузки.
