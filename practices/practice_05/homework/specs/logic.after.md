### Существующие интерфейсы: факты кода

| Интерфейс | Факт |
| --- | --- |
| parse_request(payload: dict) → PlanRequest | Проверяет Pydantic-модель, ValidationError преобразует в текстовый InputError; не отдаёт структурированный список ошибок |
| PlanRequest | departure_window; timezone=Europe/Moscow; max_options=5; boarding_buffer_minutes=10; sources; chains; лишние поля запрещены |
| planner.plan_departures(request: PlanRequest) → PlanResult | Считает без сети, возвращает словарь |
| PlanResult | TypedDict: status/options/warnings/sources/data_kind/search_scope; не модель ошибки |
| sources.load_request(path: Path или str) → PlanRequest | Читает доверенный JSON, запрещает дубли ключей и вызывает parse_request; путь не становится HTTP-параметром |
| cli.main(argv=None) | validate/plan, файловые параметры, выход 0/2 |
| server.plan_departures(request: PlanRequest) → PlanResult | MCP вызывает то же ядро; транспорт stdio |

Модель умеет принимать aware моменты с другими offset и нормализовать в
Europe/Moscow; сужение HTTP до +03:00 не меняет эту существующую возможность.
Строгие Minutes 0–1440 и max_options 1–5, уникальность ID, ссылки, связность,
хронология, до трёх этапов и 50 000 шагов перебора остаются проверками ядра.

### Алгоритм, сохраняемый только в ядре

1. Неизвестный подход/выход пропускает цепочку и отмечает неполноту.
   coverage != complete предупреждает о неполноте, не запрещая варианты.
2. Покрытие дат проверяется на возможные посадки: окно выхода плюс подход
   и запас, затем даты готовности последующих этапов с переходами.
   Пустой этап может иметь stage.source_ids для подтверждения покрытия.
3. Рейс используется при verified-источнике и применимости valid_dates к дате
   отправления; ссылки подхода/выхода проверяются на даты выхода/прибытия.
4. Выход = первый рейс − подход − запас, включён в окно. Пересадка достижима
   при отправлении не раньше прошлого прибытия + ходьба + запас перехода.
   Прибытие к цели = последнее прибытие + выход до цели.
5. Полное время — разность прибытия/выхода; ожидание — посадочный запас
   и ожидания расписанных пересадок; пересадки = число этапов − 1.
6. Ранжирование: полное время, ожидание, пересадки, выход, ID цепочки/рейсов.
   Для одинаковых начала/цели/выхода остаётся лучший путь, не более лимита.
7. Непустые варианты → ok, даже при неполноте. Пустые и полное подтверждение
   → no_routes; пустые и неполнота → needs_data. Поле complete не статус.

### Сущности

Фиксированный снимок принадлежит приложению; исходные маршрут/источники/рейсы
не редактируются пользователем. Вход формы — только параметры C-03.
Результат содержит варианты/участки и сведения о происхождении/ограничениях.
Ошибка C-05 — новая сущность адаптера, не четвёртый статус расчёта.

Учебный автобус 14.10.2026 10:40–11:40, подход 55 и выход 10 минут — оценки.
Источник synthetic: fixture, valid_dates 14 октября, checked_at 7 октября,
verified=true внутри учебного примера. Полнота не обещает поиск по всей сети.

## 3. Операции, валидация и повторы

GET /api/trip и POST /api/plan, все поля и ошибки точно определены C-02–05.
Нет прежних альтернатив по HTTP-путям или обёртке успеха: ответ — полный
PlanResult, ошибки — error.code/message с необязательным field.

Порядок: HTTP/JSON → структура → поля по C-05 → копия снимка → замена четырёх
параметров → parse_request → plan_departures → сериализация без потерь.
Порядок окна проверяется также собственным сравнением для стабильной ошибки
у конца; parse_request остаётся обязательной окончательной проверкой.
Текст InputError не разбирается для получения поля. Стартовая неисправность
снимка не выдаётся за пользовательский invalid_input или needs_data.

Поля можно менять во время pending, новую редакцию — отправлять явно.
Адаптер не разделяет mutable данные разных запросов; UI отбрасывает
старые ответы и поздние ошибки по локальной редакции/номеру. Таймаут UI
10 секунд не является обещанием серверной отмены или новым статусом ядра.
Повторы не меняют снимок; состояние последней ошибки не блокирует успех.

Точные запросы и полные ответы ядра находятся в
[contract-examples.json](../evidence/contract-examples.json), минимальные
ошибки и метаданные — в C-02/C-05. Эти наблюдения ещё не тестируют HTTP/UI.

## 4. Измеримые исходы и проверки

- **LOG-SC-001:** один исходный вариант 09:35–11:50/135; запас 20 → 09:25/145.
- **LOG-SC-002:** отрицательные окна дают no_routes и needs_data соответственно.
- **LOG-SC-003:** ошибка → исправление → успех без перезапуска и восстановления файла.
- **LOG-SC-004:** partial ok сохраняет вариант, false и все предупреждения/
  источники/область; fractional сохраняет total_minutes=135.5.
- **LOG-SC-005:** после каждого шага AS-008 вложенные данные/файл неизменны;
  последний исходный результат совпадает с первым по содержанию.
- **LOG-SC-006:** одна московская форма в разных зонах даёт одинаковый результат;
  AC1–AC5 наблюдаемы через настоящий экран, а не только API-тесты.

Границы: запас 0/1440, лимит 1/5, отказы −1/1441 и 0/6, null/bool/строка/
дробь, равное/обратное окно и offset/календарная дата. Отдельные тестовые
копии проверяют partial, неизвестную длительность и дробные минуты;
пользовательский API таких настроек не предоставляет. Полная матрица — C-07.

## 5. Допущения, границы и готовность

Один пользователь и один заранее загруженный снимок. Подключение ядра, файлы,
команды и тестовый инструмент определяются техническим plan после принятия.
Нет изменения зависимостей ядра ради оболочки. Нет произвольных адресов,
карт, API расписаний, загрузки файлов, БД, авторизации, истории и облака.

LOG-Q-001 закрыт C-02–05: точные операции/схемы, необёрнутый результат,
HTTP-коды, стабильный field для собственных проверок. LOG-Q-002 закрыт C-03:
строго +03:00 с секундами. LOG-Q-003 закрыт C-06: выбрана политика UI с
редактированием и устареванием ответов, вместо блокировки всех действий.

Общие 15 источников перечислены в [logic before](logic.before.md).
Дополнительно использованы UI before, CONTRACT и AGREEMENT. Человеческая
приёмка получена 27.10.2026; эта редакция предшествует коду и plan/tasks.
