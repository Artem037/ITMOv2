Связанные документы: [UI after](specs/ui.after.md),

## C-01. Один снимок и границы

Один маршрут `training-route`, «Учебная точка А» → «Учебная точка Б».
Источник — существующий [fixture ДЗ 4](../../practice_04/homework/tests/fixtures/rare_connections.json).
Учебная пометка: «Учебные данные: вымышленный пример, не реальное расписание».
Расписание относится к 14.10.2026; источник проверен внутри учебного снимка
07.10.2026 в 12:00 МСК. Эти даты не являются сегодняшней проверкой транспорта.

Сервер загружает и проверяет фиксированный снимок при старте; GET и POST
используют один и тот же снимок процесса, без перечитывания по запросу.
Недоступный/невалидный снимок не допускает объявления готовности сервера.
Каждый расчёт получает независимую копию всех вложенных данных. Файл, рейсы,
оценки, `coverage`, `valid_dates`, `checked_at`, `verified`, `mode` не изменяются.

HTTP доступен только на loopback. UI и API обслуживаются одним origin.
Нет пользовательских серверных путей, shell-вызовов CLI из обработчика,
сетевого получения расписаний, загрузки файлов, БД, авторизации и облака.
CLI и MCP stdio остаются самостоятельными точками входа без изменения поведения.

## C-02. Инициализация

`GET /api/trip` → HTTP 200, JSON с обязательными полями ниже. Порядок ключей
не значим; `sources` — полные сведения существующих моделей источников.
Инициализация не запускает расчёт по инициативе браузера.

```json
{
  "route": {
    "id": "training-route",
    "origin": "Учебная точка А",
    "destination": "Учебная точка Б"
  },
  "timezone": "Europe/Moscow",
  "data_kind": "fixture",
  "schedule_dates": ["2026-10-14"],
  "sources": [{
    "id": "synthetic",
    "url": "https://example.org/synthetic-timetable",
    "checked_at": "2026-10-07T12:00:00+03:00",
    "valid_dates": ["2026-10-14"],
    "mode": "fixture",
    "verified": true
  }],
  "defaults": {
    "departure_window": {
      "start": "2026-10-14T06:00:00+03:00",
      "end": "2026-10-14T12:00:00+03:00"
    },
    "boarding_buffer_minutes": 10,
    "max_options": 5
  },
  "limits": {
    "boarding_buffer_minutes": {"min": 0, "max": 1440},
    "max_options": {"min": 1, "max": 5}
  }
}
```

До загрузки метаданных расчёт недоступен. При ошибке загрузки UI показывает
понятную проблему и кнопку повторной загрузки; не придумывает defaults.
`schedule_dates` — отсортированные уникальные даты применимости источников
фиксированного снимка. `verified=true` не отменяет `mode=fixture`.

## C-03. Запрос расчёта

`POST /api/plan`, `Content-Type: application/json` (допускается `charset=utf-8`).
Тело — ровно объект из трёх ключей ниже, без дополнительных полей.
Вложенный `departure_window` содержит ровно два ключа. Все четыре значения
обязательны: серверные defaults не исправляют пропущенный ввод.

```json
{
  "departure_window": {
    "start": "2026-10-14T06:00:00+03:00",
    "end": "2026-10-14T12:00:00+03:00"
  },
  "boarding_buffer_minutes": 10,
  "max_options": 5
}
```

| Поле | Тип и допустимое значение | Ошибка поля |
| --- | --- | --- |
| `departure_window.start` | Строка `YYYY-MM-DDTHH:mm:ss+03:00`, существующие календарные дата/время, год 0001–9999 | Путь начала |
| `departure_window.end` | Тот же формат, момент не раньше начала | Путь конца |
| `boarding_buffer_minutes` | Строгое целое JSON-число 0–1440 включительно | Имя поля |
| `max_options` | Строгое целое JSON-число 1–5 включительно | Имя поля |

HTTP-вход принимает только явное московское смещение `+03:00`, с секундами,
без дробных секунд. Значения `Z`, другой offset, время без offset, пустота,
неверная дата отклоняются. Ядро шире этого договора: оно умеет нормализовать
другие явные offset. Его существующая схема при этом не меняется.

Форма вводит минуты и добавляет ровно `:00+03:00`. Конец не расширяется
до последней секунды минуты; не переносится на следующие сутки.
Зона компьютера не участвует в интерпретации введённых компонентов.
Время показывается как московское, в 24-часовом формате, с датой.

Обе границы окна включены и относятся к выходу из начальной точки, не к
отправлению автобуса и не к прибытию к цели. Равные границы допустимы.
Даты вне покрытия не запрещены форматом ввода: их смысл определяет ядро.

`null`, bool, строки с числами, дроби и JSON-числа `5.0`/`5e0` не заменяют
строгие целые; пустое поле не превращается в ноль. UI проверяет строку целиком,
затем отправляет JSON-число. Сервер не доверяет браузерной проверке.
Повторяющиеся JSON-ключи и нечисловые JSON-константы `NaN`/`Infinity`
отклоняются как некорректный JSON. Массив или скаляр вместо объекта — 422.

## C-04. Расчёт и ответ

Адаптер проверяет HTTP-форму, копирует снимок, заменяет только окно, запас
и лимит, затем вызывает существующие `parse_request(payload)` и
`planner.plan_departures(request)`. Обратный счёт, связи, полнота, сортировка
и выбор вариантов находятся только в ядре ДЗ 4.

При успешно выполненном расчёте ответ HTTP 200 — **полный `PlanResult`
без обёртки**. Обязательны `status`, `options`, `warnings`, `sources`,
`data_kind`, `search_scope`. Все вложенные сведения ядра передаются без потерь:

- Вариант: `chain_id`, `origin`, `destination`, `leave_at`, `arrive_at`,
  `total_minutes`, `waiting_minutes`, `transfer_count`, `timeline`.
- Событие: `kind`, `start`, `end`, `minutes`, `description` и все присутствующие
  `basis`, `estimated`, ID/названия остановок, `source_id`, `trip_id`, `mode`,
  `buffer_minutes`. Отсутствующие необязательные поля не выдумываются.
- Источник: `id`, `url`, `checked_at`, `valid_dates`, `mode`, `verified`.
- Область: `chains`, `departure_window`, `max_scheduled_stages`, `complete`, `claim`.

Число вариантов — от нуля до лимита. Порядок ядра сохраняется. Неизвестная
длительность не становится нулём. Длительности ответа — JSON-числа, могут
быть дробными; адаптер не округляет их. UI отображает исходное числовое
значение с русским десятичным разделителем, без усечения дробной части.
Если момент содержит ненулевые секунды, UI показывает секунды.

| `status` | `options` | `search_scope.complete` | Сообщение UI |
| --- | --- | --- | --- |
| `ok` | Непустой список | `true` либо `false` | Варианты; при false отдельно «Покрытие данных неполное» |
| `no_routes` | Пустой список | `true` | «В этом окне нет подходящих вариантов среди переданных подтверждённых цепочек» |
| `needs_data` | Пустой список | `false` | «Не хватает подтверждённых данных на запрошенное окно» и причины ядра |

Для каждого исхода видны все предупреждения, происхождение, источники и
область поиска. Формулировка области: «Лучшие среди переданных проверенных
цепочек; не поиск по всей транспортной сети». Ожидание и пересадки относятся
к расписанным этапам; городские ожидания внутри подхода включены в его оценку.

Полные рассчитанные ответы и запросы для случаев ниже сохранены в
[contract-examples.json](evidence/contract-examples.json). Этот файл —
наблюдение существующего ядра, не доказательство работающего HTTP.

| Пример | Изменение исходного тела | Точный ожидаемый результат |
| --- | --- | --- |
| normal | Нет | `ok`, complete=true, 09:35–11:50, 135 минут, ожидание 10, 0 пересадок |
| buffer20 | Запас 20 | `ok`, 09:25–11:50, 145 минут, ожидание 20 |
| no_routes | 14.10.2026 09:36:00–10:00:00, запас 10 | `no_routes`, complete=true, options=[] |
| needs_data | 15.10.2026 06:00:00–12:00:00 | `needs_data`, complete=false, options=[]; valid_dates остаётся 14 октября |
| equal_boundary | 14.10.2026 09:35:00–09:35:00, запас 10 | `ok`, выход 09:35 |
| partial | Только в тестовой копии coverage=partial | `ok`, complete=false, найденный исходный вариант и предупреждение |
| fractional | Только в тестовой копии прибытие автобуса 11:40:30 | `ok`, прибытие к цели 11:50:30, total_minutes=135.5, ride.minutes=60.5 |

`partial` и `fractional` — проверки передачи данных на тестовых копиях;
в API и форме нет возможности менять покрытие или расписание.

## C-05. Ошибки

Ошибка адаптера не является `PlanResult` и не содержит предыдущие варианты.
Схема: обязательный объект `error` с `code` и русским `message`;
необязательный `field` — только одно из четырёх имён формы выше либо
`departure_window`. UI показывает общее сообщение, если `field` отсутствует.

```json
{
  "error": {
    "code": "invalid_input",
    "message": "Число вариантов должно быть целым числом от 1 до 5.",
    "field": "max_options"
  }
}
```

Это пример HTTP 422 для `max_options="5"`. Для конца раньше начала:

```json
{
  "error": {
    "code": "invalid_input",
    "message": "Конец окна должен быть не раньше начала.",
    "field": "departure_window.end"
  }
}
```

| HTTP | Код | Условие |
| --- | --- | --- |
| 400 | `invalid_json` | Невалидный JSON, кодировка, повтор ключа или запрещённая константа |
| 415 | `unsupported_media_type` | Content-Type отсутствует или не JSON |
| 422 | `invalid_input` | Форма объекта, пропущенное/лишнее поле, тип, диапазон, дата/offset, порядок окна |
| 404 | `not_found` | Неизвестный ресурс |
| 405 | `method_not_allowed` | Неподдерживаемый метод известного ресурса; заголовок Allow |
| 500 | `snapshot_unavailable` | Проблема подготовленного снимка, если она выявлена после старта |
| 500 | `internal_error` | Неожиданный сбой; «Не удалось выполнить расчёт. Повторите запрос.» |

Все JSON-ответы имеют Content-Type application/json с UTF-8. Запрос
не меняет состояние приложения; следующий корректный вызов разрешён после
любой ошибки. 200 с пустым результатом нельзя подменять HTTP-ошибкой.
Служебные ошибки не раскрывают traceback, shell-команды или серверные пути.

Для известных четырёх полей адаптер сам формирует безопасные сообщения
и стабильный `field`; при нескольких ошибках сервер возвращает первую:
структура → начало → конец → запас → лимит → порядок окна. UI может показать
несколько своих полевых ошибок сразу. Остаточный `InputError` после сборки
запроса передаётся как общая 422-ошибка без `field`; текст ошибки не разбирается
для извлечения пути. Неисправный исходный снимок относится к ошибке приложения.

## C-06. Состояния, ожидание и повтор

До метаданных существуют загрузка/ошибка инициализации с повтором загрузки.
После загрузки: `initial`, `editing`, `invalid`, `pending`, `success`,
`no_routes`, `needs_data`, `transport_error`. Это состояния UI,
не расширение трёх статусов ядра.

1. Расчёт запускает только явная отправка. Перед отправкой UI проверяет
   поля; при ошибке сохраняет ввод, сообщает причину и фокусирует первое поле.
2. Во время запроса виден текст «Рассчитываем…». Повтор неизменённой редакции
   блокируется. Поля остаются редактируемыми.
3. Любое изменение увеличивает локальную редакцию, удаляет актуальный итог
   и делает предыдущий запрос неактуальным. UI может прервать его ожидание,
   но не рассчитывает на отмену серверного вычисления. Новая редакция может
   быть отправлена сразу после явного действия пользователя.
4. UI принимает ответ только последнего запроса текущей редакции.
   Поздний успех или ошибка старой отправки игнорируются; серверный request_id
   и хранение истории не требуются. Сервер допускает независимые вызовы.
5. Через 10 секунд ожидания актуального запроса возникает `transport_error`.
   Разрыв связи, неизвестный статус и непригодный JSON-ответ дают то же
   состояние с понятным сообщением. Автоматических повторов нет.
6. Ошибка 422 даёт `invalid` с полем/общей ошибкой; другие неуспешные HTTP
   ответы дают понятную общую ошибку с повтором. Ошибка не показывает старый итог.
7. Ответ привязан к сохранённым параметрам отправки; при результате видна
   их сводка, включая запас и лимит. Поля не сбрасываются после неудачи.
   Повтор одинакового запроса даёт равное содержимое результата.
