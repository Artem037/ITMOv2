# Планировщик загородных поездок

Помоги выбрать время выхода с минимальным полным временем в пути среди
проверенных цепочек. Расчёт выполняет собственный MCP `trip_planner` с
инструментом `plan_departures`; в OpenCode имя обычно отображается как
`trip_planner_plan_departures`. Ответ пользователю — по-русски.

## От запроса к маршруту

1. Уточни недостающие исходные данные: точку старта и цель, дату, окно выхода,
   приемлемый пеший участок. Уже сообщённое повторно не спрашивай. Точный
   домашний адрес можно заменить общественным ориентиром; не переноси его
   в учебные evidence без необходимости. Запас на первую посадку по умолчанию
   10 минут, на пересадки — предложи явно с учётом перехода.
2. Найди разумные пространственные цепочки, проверь остановки и направление.
   Для сбора источников используй доступные fetch MCP/браузер, а для данных
   и вызова инструмента — [формат и источники](references/input-and-sources.md).
   В этой версии нет адаптера Яндекс API: агент извлекает расписания из
   официальных страниц и нормализует их. Если источник недоступен, запроси
   недостающие данные или проверь другую цепочку.
3. Для каждого рейса нужны точные отправление/прибытие на нужных остановках
   и применимость к дате поездки. Часы с конечной не дают времени промежуточной
   остановки. При конфликте источников выясни актуальность; не выбирай
   удобные часы. Городской участок и пешие переходы допустимо оценить по
   карте, сохранив основание. Редкий городской автобус тоже требует расписания.
   Сопоставь описания подходов с первым/последним транспортом: если вход
   противоречив, объясни несоответствие до выдачи пользовательского маршрута.
4. Подготовь `PlanRequest` по схеме MCP и проверь его CLI `validate` из
   справки. Неподтверждённый источник остаётся `verified: false`, неизвестная
   длительность — `null`, неполное покрытие — `partial`/`missing`.
   Перед реальной выдачей обнови проверку источников на нужную дату.
   Пустое расписание требует отдельного подтверждённого источника этапа;
   старый снимок не доказывает отсутствие рейсов на новой дате.
5. Вызови MCP `plan_departures` с объектом `request`. При ошибке исправь
   конкретное поле и повтори вызов. Ошибку подключения сообщи явно; результат
   CLI нельзя описывать как состоявшийся MCP-вызов. При `needs_data` назови
   недостающие данные. `no_routes` относится только к проверенным цепочкам
   и окну, а не ко всей транспортной сети.
6. Представь результат по [примеру](references/output-example.md): до пяти
   уникальных вариантов, затем пошаговый лучший маршрут, источники и
   ограничения. Используй готовые времена и метрики MCP, не меняй запас
   молча ради красивой пересадки. Если вариантов меньше пяти, объясни это.
   MCP оставляет лучший маршрут для каждого времени выхода: более медленный
   путь с тем же выходом не занимает ещё одно место в списке.

## Границы результата

Полное время включает городской путь, ожидание, переходы и последний
пеший участок. Порядок: полное время → ожидание → пересадки → выход.
До трёх участков с точным расписанием; это ограничение первой версии.
Сложную цепочку нельзя скрывать внутри «оценочного подхода», если там есть
редкие отправления. Длинную прогулку явно покажи и сопоставь с пожеланиями.

`data_kind: fixture` или `mixed` означает, что результат содержит
вымышленные данные; его можно показать как учебный расчёт, но не как
действующий маршрут. В реальном результате отличай точные часы расписания
от оценок городской дороги и пеших участков. Запас уменьшает риск опоздания,
но не гарантирует отсутствие задержек.
