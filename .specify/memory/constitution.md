# ITMOv2 Transit Planner Constitution

## Core Principles

### I. Одно расчётное ядро и совместимость

Новые интерфейсы MUST использовать существующие `parse_request` и
`plan_departures` из ДЗ 4. Копирование алгоритма в браузер или второй пакет
запрещено. Действующие CLI `validate`/`plan`, MCP stdio, схемы входа/результата
и обработка ошибок MUST сохранять прежнее поведение. Новая обёртка не заменяет
собственный MCP: все точки входа используют одну проверяемую арифметику.

### II. Честные данные и московское время

Учебные данные MUST быть явно помечены; оценки нельзя представлять как точные
расписания. Смена окна поездки MUST NOT сдвигать рейсы или менять `valid_dates`,
`checked_at`, `verified`. Время пользователя трактуется в `Europe/Moscow`,
независимо от зоны компьютера. Неизвестная длительность не равна нулю.
`no_routes`, `needs_data`, `ok` с неполным покрытием MUST сохранять различия;
ограничения поиска, предупреждения и источники нельзя скрывать.

### III. Две спецификации и решение человека до кода

Одна история MUST иметь две независимые исходные спеки UI и логики, общий
контракт и две версии после согласования. До реализации человек MUST принять
конкретные спеки и контракт. Общая feature-spec Spec Kit и принятие BRIEF
не заменяют эту приёмку. Новые решения по данным, вызовам, ошибкам и состояниям
сначала отражаются в документах, затем в коде; before-версии сохраняются.

### IV. Проверяемые изменения

Новое поведение приложения MUST проходить focused test → ожидаемый RED →
минимальная реализация → GREEN. Существующие тесты выполняются как регрессия;
запрещено ослаблять runner или hook, чтобы скрыть сбой. Перед завершением
выполняются `sh scripts/check.sh` и `git diff --check`; при интеграции также
`make test` и новые проверки. Сквозное доказательство MUST включать настоящий
UI и расчёт, успех и ошибку/границу. Моки и API-тесты сами по себе его не заменяют.
Сохраняются фактические команды, выводы и коды завершения.

### V. Одна небольшая локальная история

ДЗ 5 MUST продолжать планировщик ДЗ 4: один экран повторного расчёта одного
подготовленного датированного маршрута. Новая часть запускается локально; HTTP
слушает loopback. В эту историю не входят адресный поиск, карты, живые API,
авторизация, хранение поездок и облачный деплой. Во время запроса нельзя
запускать shell-команду из пользовательских данных или принимать путь к
произвольному серверному файлу. Расширение объёма требует решения человека.

## Project Constraints

- Ядро: Python 3.12+, uv и lock-файл ДЗ 4; существующие SDK/Pydantic не обновлять
  ради новой оболочки. UI: HTML/CSS/JavaScript без UI-фреймворка.
- Ядро остаётся в `practices/practice_04/homework/trip_planner/`; материалы и
  новая часть ДЗ 5 — в `practices/practice_05/homework/`.
- Сохраняются готовые skills, hook, конфигурация MCP, отчёты и результаты
  других практик. Посторонние локальные файлы не включаются автоматически.
- Разработка ДЗ 5 идёт в `practice_05`. Spec Kit не создаёт Git-ветки;
  публикация и PR выполняются только по отдельному поручению пользователя.
- Основное демо использует реальный датированный снимок; fixture остаётся отдельным контрольным запуском для тестов. Во время расчёта LLM и сеть не требуются. Расширение принято пользователем 29.10.2026.

## Development Workflow

Принятый BRIEF → constitution и общая feature-spec → два отдельных чата и
две before-спеки → общий контракт и две after-спеки → решение человека →
технические plan/tasks → реализация → регрессия/браузерные проверки → демо.

Координатор владеет constitution, общей feature-spec и активным каталогом
Spec Kit. Команды не перезаписывают общие файлы параллельно. В проверках
всегда указывается, что реально выполнено: базовый расчёт, UI, MCP или
сквозной сценарий. Отсутствие существенных расхождений фиксируется честно;
искусственные ошибки для отчёта не создаются.

## Governance

Эта первая версия закрепляет принятый BRIEF и существующие правила проекта.
Изменения принципов MUST быть видимы человеку и сопровождаться причиной и
проверкой связанных спецификаций. Несовместимое изменение правил повышает
major, новый принцип — minor, редакционная правка — patch. Перед реализацией
и при итоговом review проверяется соблюдение constitution. Шаблоны Spec Kit
читают этот файл во время workflow; их исходные файлы здесь не изменяются.
Последние явные решения пользователя имеют приоритет над устаревшим описанием
предыдущей домашки; ограничения задания сохраняются.
