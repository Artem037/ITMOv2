## Термины и устройство

**Модель** генерирует текст по входным данным. **Агент** использует модель
в цикле: получает задачу, выбирает инструмент, получает его результат,
решает следующий шаг. **OpenCode** организует этот цикл, работу с файлами,
чат, разрешения и подключения. В ДЗ 3 **Ollama** запускает локальные веса
и предоставляет OpenCode API по адресу `http://localhost:11434/v1`.

**Skill** — пакет инструкций для повторяемой задачи. `SKILL.md` содержит
название, описание того, когда применять skill, и порядок работы.
Справки в соседних файлах дают подробный формат и примеры. OpenCode
загружает содержимое через инструмент `skill`. Наш `transit-trip-planner`
задаёт процедуру сбора ограничений, проверки расписаний, вызова калькулятора
и объяснения маршрута. [Устройство skills в OpenCode](https://opencode.ai/docs/skills/).

**MCP — Model Context Protocol** — протокол подключения программ к приложению
агента. OpenCode выступает host и использует MCP-клиент, наша Python-программа
выступает сервером. Сервер описывает доступный **tool**, его аргументы и
результат. Агент выбирает вызов, OpenCode передаёт аргументы программе,
программа выполняет вычисление и возвращает ответ.
[Архитектура MCP](https://modelcontextprotocol.io/docs/learn/architecture).

У нас сервер `trip_planner`, tool `plan_departures`; в OpenCode вызов
виден как `trip_planner_plan_departures`. Соединение **stdio** означает
обмен сообщениями через стандартный ввод и вывод локального процесса.
OpenCode сам запускает его по команде из `opencode.json`.

**Tool** — конкретная выполняемая операция. `read` читает файл,
`trip_planner_plan_departures` считает маршрут. Skill объясняет агенту
порядок действий; код инструмента выполняет расчёт. Встроенный `webfetch`
и инструмент готового fetch MCP имеют разные подключения, хотя оба
могут получать веб-страницы.

**AGENTS.md** содержит постоянные правила проекта: ограничения,
обязательные проверки и разрешённые изменения. В домашке он требует
проверять источники, различать тестовые и реальные данные, запускать runner.

**Hook** — обработчик события. Наш plugin реагирует на значимую правку
через инструмент OpenCode, запускает `scripts/check.sh` и добавляет
PASS/FAIL к результату этого инструмента. **Runner** — сам скрипт проверок.
Он запускает Ruff и тесты. **Ruff** проверяет стиль и формат Python-кода.
**Pre-commit** запускает настроенные проверки при `git commit` для файлов
Notify Mini; `git add` только подготавливает индекс. На защите hook
демонстрируется сразу после правки, без создания коммита.

**TDD** — сначала тест с ожидаемым поведением и его падение, потом реализация
до успешного теста, затем упрощение кода при сохранении результата.
Готовый TDD skill применялся при разработке; собственный транспортный skill
применяется при решении пользовательской задачи.

## ДЗ 3 — что делали

Подключили локальный Qwen через Ollama к OpenCode. Подготовили помощника
`local-guide`, который может читать и искать файлы, и проверили, правильно
ли он отвечает на вопросы о небольшом сервисе Notify Mini.

Notify Mini хранит имена подписчиков в множестве `subscribers` в памяти
процесса. `subscribe` убирает внешние пробелы, отвергает пустое имя и
добавляет имя. Два вызова для Ann допустимы; имя остаётся одно. После
перезапуска данные теряются, поскольку сохранение в файл или БД не реализовано.

Для модели использованы `qwen3.5:4b` и производный тег `itmo-agent`.
На проверенном ноутбуке Apple M5, 16 GiB RAM. Размер весов около 3,4 GB;
загруженная модель с рабочими структурами занимала около 5,6 GB.

**Modelfile** задаёт основу `FROM`, параметры и, при наличии, `SYSTEM`.
`Modelfile.agent` устанавливает контекст 65536 и temperature 0.2;
инструкция помощника находится отдельно в `repo-system.txt`.
Модели `itmo-local` и `itmo-local-relaxed` использовались в дополнительных
экспериментах со строгим и ослабленным SYSTEM.
[Назначение Modelfile](https://docs.ollama.com/modelfile).

Контекст измеряется в токенах: это объём инструкций, истории и прочитанных
данных, который модель может учитывать. Квантизация Q4_K_M уменьшает расход
памяти на веса. Изменение system prompt меняет инструкции, веса сохраняются.
Temperature влияет на выбор продолжения; увеличение не гарантирует улучшения.

### Учебный результат через skill и MCP в OpenCode

Из корня ДЗ 4 запусти:

```sh
opencode --model vsellm/openai/gpt-5 --agent build
```

Для этой работы обычный запуск загружает проектный after-edit plugin.
Флаг `--pure` из ДЗ 3 сюда не добавляй — он отключил бы внешние плагины.

Первый запрос в чат:

```text
Демонстрируем домашнюю работу 4. Прочитай AGENTS.md.
Загрузи skill transit-trip-planner и прочитай его две справки.
Возьми practices/practice_04/homework/tests/fixtures/rare_connections.json.
Вызови собственный MCP trip_planner_plan_departures с объектом request
из файла. Покажи время выхода, прибытия, полное время и timeline.
Файлы не изменяй. Явно укажи, что данные вымышленные.
```

Проверь действия: `read`, `skill`, `trip_planner_plan_departures`.
Если агент лишь описал намерение, попроси выполнить инструмент.
Если он посчитал через bash/CLI, попроси именно MCP-вызов.

Учебный автобус отправляется в 10:40, подход занимает 55 минут,
начальный запас — 10. Выход: **10:40 − 55 − 10 = 09:35**.
Автобус прибывает в 11:40, последний подход — 10 минут, цель в **11:50**.
Общее время: **55 + 10 + 60 + 10 = 135 минут**. Ожидание/запас — 10 минут.
`data_kind: fixture` означает учебные данные. Получится один вариант;
ещё четыре вымышленных рейса не добавляются.

Второй запрос в тот же чат:

```text
Теперь покажи ошибочный вход собственного MCP. Возьми тот же request,
в памяти поменяй boarding_buffer_minutes на -1 и вызови
trip_planner_plan_departures. Это намеренный невалидный запрос:
не исправляй его до вызова. После полученной ошибки вызови снова с 10.
Файл на диске не меняй. Покажи фактическую ошибку и следующий успех.
```

Ожидается ошибка в поле `request.boarding_buffer_minutes`: значение
должно быть неотрицательным. Следующий правильный вызов снова даёт 09:35.
Это проверяет вход и то, что ошибка не сломала сервер.


CLI показывает тот же расчёт. `mcp-smoke` поднимает настоящий сервер и
проверяет протокол. Для критериев применения агентом покажи и вызов в чате.
Запуск `python -m trip_planner.server` сам по себе будет ожидать сообщения
stdio; человеческий вопрос в этот процесс вводить не нужно.

### Автопроверка FAIL и PASS

Это короткая демонстрация в том же чате Build. Сначала в другом терминале
из корня ДЗ 4 сохрани копию одного теста:

```sh
cp practices/practice_04/homework/tests/test_planner.py \
  /tmp/itmo-test-planner-defense.py
```

Запрос в OpenCode:

```text
Покажи after-edit hook одной намеренной правкой теста.
В practices/practice_04/homework/tests/test_planner.py внутри
test_departure_is_0935 поменяй ожидаемое total_minutes с 135 на 134.
Используй edit или apply_patch. Другие файлы не меняй.
Это демонстрация: после правки остановись, не исправляй ошибку
и не запускай runner вручную. Покажи результат, добавленный hook.
```

Результат инструмента правки должен содержать `[Practice 4 check: FAIL]`
с деталями: реальный результат 135, неправильное ожидание 134.
Затем запрос:

```text
В том же тесте верни правильное ожидание 135 через edit или apply_patch.
Другие файлы не меняй. Покажи автоматический PASS из результата правки.
```

Hook запускает общий runner и возвращает PASS. Проверь восстановление:

```sh
cmp /tmp/itmo-test-planner-defense.py \
  practices/practice_04/homework/tests/test_planner.py
git diff -- practices/practice_04/homework/tests/test_planner.py
```

Обе команды должны не показать различий. Если сессия оборвалась до
восстановления, верни копию и проверь проект:

```sh
cp /tmp/itmo-test-planner-defense.py \
  practices/practice_04/homework/tests/test_planner.py
sh scripts/check.sh
```

Изменение обычным редактором вне OpenCode не запускает этот after-edit hook.
Ручной запуск runner помогает восстановиться; живой показ hook требует
правки через инструмент агента.

### Реальный маршрут и ограничения ДЗ 4

Дополнительный показ на сохранённом расписании:

```text
Используй transit-trip-planner. Рассчитай через собственный MCP данные
practices/practice_04/homework/examples/tolmachevo-2026-10-14.json.
Покажи три варианта и отдельно объясни оценки городского и пешего пути.
Это воспроизведение сохранённого снимка; дату источников не обновляй
без фактической повторной проверки и файлы не меняй.
```

| Выход | Электричка Балтийский → Толмачёво | Каньон, оценка | Полное время |
|---|---|---|---|
| 07:17 | 7451, 08:37–10:00 | 11:55 | 4 ч 38 мин |
| 07:23 | 6111, 08:43–10:44 | 12:39 | 5 ч 16 мин |
| 08:16 | 7413, 09:36–11:41 | 13:36 | 5 ч 20 мин |

Источники проверены 08.10.2026 для поездки 14.10.2026. Подход до электрички
70 минут оценочный, запас на посадку 10 минут отдельно. После Толмачёва
115 минут и около 9,2 км пешком, оценка карты. Промежуточное автобусное
время у Плоского не удалось подтвердить. Пользователь ещё не принял длинную
прогулку, поэтому это условная альтернатива. Подробности:
[реальный пример](../practices/practice_04/homework/evidence/real-route.md).

Лучший вариант определяется среди переданных проверенных цепочек.
В этой версии нет Яндекс API-адаптера; страницы собирает агент,
MCP считает. Максимум три расписанных этапа и до пяти разных выходов.
Городские длительности оценочные. `transfer_count` и `waiting_minutes`
относятся к расписанным этапам: пересадка метро и ожидание внутри городского
подхода объясняются отдельно. Неподтверждённое расписание — `needs_data`,
доказанное отсутствие подходящей комбинации — `no_routes`, неверная
структура запроса — ошибка валидации.

## Короткие ответы на вопросы ревьювера

- Зачем skill? Чтобы повторять процедуру сбора и проверки данных, затем
  правильно вызывать расчёт и объяснять его границы.
- Зачем MCP? Чтобы предоставить агенту нашу проверяемую Python-функцию
  со схемой входа и структурированным результатом.
- Где арифметика? В `planner.py`; CLI и MCP используют её совместно.
- Откуда расписание? Из проверенных страниц, с URL, датой проверки и
  применимыми датами; демонстрационный fixture явно вымышленный.
- Зачем hook? Чтобы агент получил результат проверки сразу после правки
  и мог реагировать на фактическую ошибку.
- Почему есть CLI? Человек может воспроизвести расчёт без модели и MCP-host.
- Почему иногда меньше пяти вариантов? Подтверждённых допустимых выходов
  меньше; ответы не дополняются выдуманными рейсами.
- Локальный MCP означает локальную модель? Расположение сервера и модели
  независимо: ДЗ 3 использует локальную Ollama; в ДЗ 4 настроена облачная
  модель VseLLM, а расчётный сервер работает на ноутбуке.
