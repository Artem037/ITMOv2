## Принятая одна фича

**История:** «Как пользователь планировщика, я хочу задать окно выхода и запас на посадку в локальной форме для подготовленного маршрута, чтобы увидеть подходящие времена выхода и понять причины отсутствия результата».

Один экран: описание подготовленного маршрута и даты его данных, окно выхода по Москве, запас на посадку, число вариантов от 1 до 5 и кнопка расчёта. Результат показывает выход/прибытие, продолжительность, участки пути, предупреждения и источники. Для минимального демо достаточно одного явно помеченного учебного снимка; каталог маршрутов и загрузка произвольных файлов не нужны.

Объём принят в BRIEF 22 октября. Общая feature-spec записывает его для дальнейшей работы команд; отдельные UI/logic-спеки и контракт ещё предстоит согласовать до кода.

### Пять принятых условий BRIEF

1. Для учебного `rare_connections.json`, окна 14.10.2026 06:00–12:00 и запаса 10 минут форма вызывает настоящий расчёт и показывает выход 09:35, прибытие 11:50, 135 минут пути. Учебный характер данных виден.
2. Допустимые параметры пересчитывают результат ядром. Неправильное окно/значение поля показывает понятную ошибку; после исправления можно успешно повторить расчёт.
3. Для окна 14.10.2026 09:36–10:00 отображается `no_routes`: вариантов нет среди переданных подтверждённых цепочек. UI не заявляет отсутствие транспорта вообще.
4. Для даты 15.10.2026 при неизменном учебном снимке отображается `needs_data`. Расписание не сдвигается, нехватка данных не маскируется под отсутствие маршрутов.
5. UI сохраняет предупреждения, происхождение данных и область поиска; старые CLI/MCP-сценарии и тесты продолжают работать.

**За рамками:** свободный поиск по адресам, геокодинг, карты, сбор живых расписаний, Яндекс API, автоматическая проверка свежести, авторизация, база, история поездок и облачный деплой. Реальный пример прошлой поездки остаётся историческим примером; основное демо использует fixture.

## Переиспользование и границы контракта

| Компонент | Назначение |
| --- | --- |
| `practices/practice_04/homework/trip_planner/models.py` | `parse_request(payload) → PlanRequest`, структура, время, ссылки и бюджет перебора |
| `practices/practice_04/homework/trip_planner/planner.py` | `plan_departures(request) → PlanResult`, расчёт и ранжирование |
| `practices/practice_04/homework/trip_planner/cli.py` | Проверка/расчёт из JSON; сохранить команды и коды завершения |
| `practices/practice_04/homework/trip_planner/server.py` | Действующий MCP stdio; новый адаптер его не заменяет |
| `practices/practice_04/homework/tests/fixtures/rare_connections.json` | Воспроизводимый учебный снимок на 14.10.2026 |
| `.opencode/skills/transit-trip-planner/` | Существующий skill подготовки данных; форма не имитирует его сетевую работу |

Факты существующего ядра, обязательные для новой спецификации:

- `departure_window.start/end` — timezone-aware ISO datetime, нормализация в `Europe/Moscow`, `end >= start`, границы включены. Браузерный `datetime-local` не содержит offset: московское время преобразовать явно, независимо от зоны компьютера.
- `max_options` — строго целое 1–5, default 5. `boarding_buffer_minutes` — строго целое 0–1440, default 10. Пустое поле не превращать в ноль.
- `PlanResult.status`: `ok`, `no_routes`, `needs_data`. Невалидный ввод — отдельная ошибка адаптера, не четвёртый статус ядра.
- `ok` возможен при `search_scope.complete=false`: найденные варианты сохраняются вместе с предупреждением о неполноте.
- Ответ включает `options`, `warnings`, `sources`, `data_kind`, `search_scope`. У варианта есть `leave_at`, `arrive_at`, длительности, `timeline`; минуты могут быть дробными.
- Неизвестное время подхода/выхода (`null`) не равно нулю. Ядро ранжирует только переданные цепочки, не ищет путь между произвольными адресами и не подтверждает источники сетевым запросом.

Предложение для адаптера: взять подготовленный снимок, скопировать, применить только разрешённые параметры формы, вызвать существующие `parse_request` и `plan_departures`, вернуть полный результат. Не принимать произвольный серверный путь. Точные операции, коды ответов, ошибки и преобразование типов согласовать на этапе 4.
